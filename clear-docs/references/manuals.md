# Manuals and exported documents

Create a manual when the reader needs an offline, printed or shared document. Agree on its audience and purpose from the request. Do not concatenate every developer note into a book.

Keep the opening useful: how to start, how to find the main controls, and where to get help. Move exhaustive contracts and implementation details into an appendix only when they belong in the same deliverable.

Use real heading levels, a small type system and enough space for scanning. Keep a figure beside the text it explains. Avoid pages filled with identical tables or decorative cards.

For a designed handbook, use a coherent cover and chapter openings. Match the requested theme across the full document, including page backgrounds, tables, callouts and links. A dark product manual should stay dark throughout unless the owner asks for a print edition. Banners can carry topic-specific artwork. Give diagrams enough space to read their labels. Use fewer, larger figures rather than a gallery of tiny previews.

Keep only useful page navigation in the margins. Page numbers and a clickable contents page are usually enough. Remove recurring product labels, chapter labels, version footers, "Keep reading" lines and captions that repeat what the figure already says. Put necessary edition details in one place. Keep links and qualifications beside the decisions they affect or in a concise reference page.

Choose the format for the job. Markdown is suitable for maintained web guides. LaTeX suits an explicitly requested typeset manual. Word suits collaborative editing. A format change cannot fix confusing prose.

Render the complete document. Inspect every page for clipped text, awkward breaks, tiny figures, missing fonts and repeated blank space. Check links and contents after the final edit. Keep the editable source with the delivered file.
